# 员工工作日志：工作计划、三星目标评定、全员状态表与云端档案库计划书

日期：2026-10-13  
状态：已确认，待实施

## 一、目标与现状

在现有信纸式工作日志的底部增加员工填写的工作计划，并让审批人在员工姓名、日期左侧选择目标结果。员工提交后，审批人应看到包含工作计划的完整信纸；审批结果、逐项批注以及员工提交和各级审批的具体时间应在日志中显示。同时增加一张所有已登录人员都能查看的员工日志状态表，便于按日期查看谁已提交、谁已归档；员工提交版和领导审批版分别留存在阿里云 OSS 私有档案库，供有权限的领导在系统界面查阅。

目前信纸底部只有员工姓名和日志日期。现有整篇日志颜色中，绿色表示“已提交/已退回”，红色和灰色用于核查结果。因此，新三星目标评定应独立存储，不能直接复用现有绿色状态，否则旧日志和统计会产生歧义。

## 二、页面与交互

信纸底部采用三栏：左侧“工作计划”，中间“三星目标评定”，右侧沿用自动生成的员工姓名和日志日期。窄屏时依次纵向排列，打印时保留计划、结果和署名。

```text
┌──────────────────────────────────────────────────────────────┐
│ 工作计划                 目标评定              员工姓名：张三 │
│ 计划完成时间：____       ☆ 目标达成           日志日期：____ │
│ 目标：____________       ☆ 延期完成                         │
│                        ☆ 目标未完成                         │
└──────────────────────────────────────────────────────────────┘
```

1. 每份日志先提供一条工作计划，包含“计划完成时间”（日期和时分）与“目标”文字。员工可在草稿及退回修改时填写；提交后只读。姓名和日志日期仍由系统生成，不由员工填写。
2. 三颗星从左到右分别代表：红色＝目标达成，绿色＝延期完成，灰色＝目标未完成。初始均为空心无色；审批人点击其中一颗时仅该星着色，另外两颗保持空心。提交审批前可改选，提交后该次结果只读。
3. 员工只看到星级结果，不能为自己的目标评星。当前审批人（领导、管理层或管理员）在审批完整信纸时选择一颗星，并继续对每项工作分别批注。
4. 每位审批人提交后，员工端展示最新一次已提交的目标评定，并在审批记录中保留各审批人的选择、姓名和时间；后续审批不会抹去前序记录。员工页面打开期间应自动刷新，目标是在审批提交后 5 秒内显示。
5. 审批人选择“退回修改”时不产生目标评定。员工修改计划并重新提交后，信纸上的当前评定重新显示为无色；前一轮审批记录继续留存。

## 三、数据与规则

| 内容 | 建议规则 |
| --- | --- |
| 工作计划数量 | 本期每日日志一条；不增加多计划管理界面。 |
| 计划完成时间 | 员工通过日期和时间选择控件选定，按北京时间解释并保存为明确时区的时间值；正式提交时必须晚于提交时刻，保证有提醒窗口。 |
| 目标文字 | 去除首尾空白后必填，最多 500 字；不套用工作内容“每项至少 20 字”规则。 |
| 草稿 | 允许计划暂未填完，继续保存。 |
| 新日志提交 | 计划完成时间与目标必须同时有效，否则提示具体缺失字段并阻止提交；服务端再次校验。 |
| 旧日志 | 新字段允许为空，历史日志照常显示和查询，不追溯阻止或改写旧数据。 |
| 目标评定 | 有工作计划的审批确认必须三选一；服务器核验当前审批人权限与选择值。 |
| 延期完成 | 由审批人依据计划时间、实际情况和逐项批注判断，不由系统仅凭审批时间自动推断。 |

新计划信息随日志草稿保存，提交时写入版本快照。每位审批人的目标评定写在其审批步骤中，供员工历史日志、领导日志详情和审计记录读取。新结果字段使用独立的“达成／延期／未完成”枚举；现有日志状态和颜色含义保持原样。

## 四、全员工作日志状态表

在侧边栏增加“全员日志状态”入口，员工、领导、管理层和管理员登录后均可查看。页面默认显示北京时间的今天，可切换日期查看历史；每个已启用且未删除的员工在选定日期占一行，即使当天没有日志也要显示。领导和管理员账号本身不列入需要交日志的员工名单。

| 工号 | 姓名 | 是否完成工作日志 | 是否归档 |
| --- | --- | --- | --- |
| 001 | 张三 | 是 | 否 |
| 002 | 李四 | 是 | 是 |
| 003 | 王五 | 否 | 否 |

**“完成工作日志”指该日期日志已经正式提交，不等于目标达成。**日志状态为“已提交”“审批中”或“已归档”时显示“是”；无日志、仅有草稿或被退回待重交时显示“否”。**“是否归档”须同时满足：全部审批完成，且本轮最终审批版已成功上传阿里云 OSS，才显示“是”。**仅员工提交版上云、只完成部分审批，或全部审批完成但最终审批版仍待上传/上传失败时，均显示“否”。隔天完成审批或上传成功后，原日志日期那一行的归档值随之更新。三星颜色不参与这两个“是/否”字段的计算。

现有账号只有用户名和系统生成的用户 ID，没有真实工号。计划新增独立且唯一的工号字段，由管理员在用户管理中填写或修改。旧账号与刚自行注册的账号在补录前显示“待补录”；不把用户名或内部 ID 冒充工号。

**查看权限分层：**所有已登录人员从表格接口只看到工号、姓名及两个“是/否”状态，接口不传日志正文、图片和批注；仅对有权限的领导额外返回该行已提交日志的详情标识，用于打开“查看日志”入口。普通员工在这张表中不能打开同事的日志；本人仍可在“今日日志/历史日志”查看自己的内容。只有对该员工拥有查看权限的领导账号（LEADER），在已有正式提交的日志行上看到“查看日志”入口，并通过服务端权限校验打开完整信纸。管理层和管理员在此表中不显示详情入口，其现有独立日志管理入口保持原样；未提交的草稿及退回后正在修改的内容不通过此入口公开。

## 五、提交与逐级审批时间线

员工正式提交日志时，系统记录实际提交时刻；部门主管（使用现有“领导”角色）及后续审批人每次点击“确认审批”时，分别记录各自审批生效的时刻。完整信纸的审批记录区按流程顺序展示“操作人姓名／审批级次或身份／动作／具体时间”，员工在自己的历史日志、具有查看权限的审批人在日志详情中都能看到。例如：

```text
员工提交      张三       2026-10-13 17:42:08
第 1 级领导（部门主管）审批通过 李主管 2026-10-13 18:03:27
第 2 级领导审批通过            王经理 2026-10-14 09:12:51
```

1. 时间统一按北京时间显示，格式为 `YYYY-MM-DD HH:mm:ss`，精确到秒；由服务端在操作成功时生成和保存，用户不能手填或修改。信纸上的“日志日期”、工作计划的“计划完成时间”与这些实际操作时间分开显示，不能互相替代。
2. 部门主管沿用现有 `LEADER` 角色，不新增单独的“部门主管”角色。审批级次按现有审批链确定，显示实际审批人的姓名、领导身份及级次；各级领导分别显示自己的审批时间，不能用最终归档时间代替。界面不因审批级次自动推断额外职务。
3. 未正式提交的草稿不显示提交时间；待审批步骤显示“待审批”，不显示虚构时间。退回修改显示退回人及退回时刻，动作明确写“退回修改”，不算“审批通过”。
4. 退回后重新提交视为新一轮提交，产生新的提交时间；旧轮的提交、退回、审批时间保留在历史记录中。当前轮和历史轮分组展示，避免把旧审批时间误认为本轮结果。
5. 全员状态表仍只提供约定的四列状态，不向全员增加日志时间线或详情；时间线遵循日志正文的现有权限控制。

现有数据已包含日志的 `submittedAt` 和每个审批步骤的 `actedAt`，但提交时间尚未完整提供给页面，审批页面目前只显示到分钟。实施时复用这些字段；对多轮提交补充可追溯的每轮提交时间记录，不以会被下一轮覆盖的单个 `submittedAt` 充当全部历史。旧记录若缺失具体时间，显示“历史记录未保存时间”，不得推算或补造。

## 六、工作计划到期前双向提醒

员工在信纸中用日期、时间选择控件设定计划完成时间。计划尚未评定且临近该时间时，系统向员工本人和该日志审批链中具备 `LEADER` 角色的审批人发送**站内提醒**；员工一条、每位对应领导各一条，分别记录已读状态，不通知无关领导。提醒写明员工姓名、目标摘要、计划完成时间，并链接到各自有权限查看的日志页面；领导只能打开其授权范围内的完整日志，不向其他员工泄露目标内容。

本期复用“系统设置”的“提前提醒（分钟）”，现有默认值为 **30 分钟**。例如计划完成时间为北京时间 18:00，提前量为 30 分钟，则在 17:30 起的下一次定时检查中生成提醒；定时任务目前每分钟运行一次，因此不承诺恰好在 17:30:00 到达。该提前量与日志提交提醒共用，管理员修改后两类提醒都会受影响。

每份日志的当前计划每位接收人只提醒一次；定时任务重跑或服务重启不得重复推送。草稿、未填写计划的旧日志、已退回待修改的日志以及已作出目标评定的日志不发送计划提醒。员工修改计划时间并重新提交后，按新一轮提交及新时间重新计算提醒；旧轮提醒保留为历史，不误指向新计划。计划时间已经过去时不补发“到期前提醒”。

## 七、阿里云 OSS 云端档案库

1. **留存两个阶段的完整版本。**员工每次正式提交（含退回后重提）成功后，生成“员工提交版”；部门主管即现有 `LEADER` 审批通过后，生成“领导审批版”。若审批链还有后续审批人，每次审批通过也各生成一个新版本，直到最终审批版。各版本独立保存、不覆盖，注明日志 ID、提交轮次、版本类型、操作人和操作时刻。退回不冒充审批通过；原提交版继续保留。
2. **保存完整信纸内容。**每个版本包含该时点的全部工作项、图片、工作计划、员工姓名与日志日期、已产生的逐项批注、三星评定及提交/审批时间线；领导打开历史版本时看到的是当时的信纸，不因后续修改或重提改变。云端档案是独立快照，不只保存当前数据库记录的链接。本期通过系统页面还原信纸样式，不额外要求 PDF 导出。
3. **私有存储与授权。**使用与当前上海 ECS 同地域的 OSS 私有 Bucket；服务端通过同地域内网访问，优先使用 ECS 实例 RAM 角色及仅限档案前缀的最小权限。Bucket 名称与角色由部署时配置，不写入前端或仓库。浏览器不直接持有 OSS 凭据或永久公开链接；每次查阅先由应用校验登录身份和该员工日志的查看范围，再由服务端读取档案。技术依据：[OSS 内网访问](https://www.alibabacloud.com/help/en/oss/user-guide/access-oss-via-bucket-domain-name)、[OSS 私有权限](https://www.alibabacloud.com/help/en/oss/user-guide/object-acl)、[实例 RAM 角色](https://www.alibabacloud.com/help/en/ram/user-guide/ram-role-overview)。
4. **领导界面直接可见。**在现有 `LEADER` 侧边栏增加“云端档案库”入口。列表可按员工姓名/工号、日志日期检索，并显示“员工提交版”“第 N 级领导审批版”、保存时间和上传状态；点击某个已上传版本，在系统内打开完整信纸及该版本已有批注。管理层和管理员沿用现有日志查看权限访问档案库；普通员工看不到云端档案库入口，但仍能在自己的历史日志查看本人内容及批注。仅隐藏入口不构成授权，列表与下载接口也必须做服务端权限检查。
5. **失败与重试。**日志提交或审批先在数据库成功保存，再异步上传对应快照到 OSS；上传失败不丢失业务记录，也不伪称该版本已在云端。系统记录“待上传／已上传／上传失败”，失败任务可安全重试，按日志、轮次、阶段和审批级次去重，重复执行不生成错误的额外版本。只有 OSS 确认保存后才允许从档案库打开该版本；对失败保留可排查的错误记录。全员表的“是否归档”读取**当前提交轮次的最终审批版**上传结果；前一轮或中间审批版成功上传不能替代。

## 八、实施顺序

1. **数据与接口**：增加工作计划、审批步骤目标评定和独立工号字段及数据库迁移；扩展草稿、提交、审批、查询响应；增加按日期汇总全体在职员工提交与归档状态的只读接口；保留旧日志兼容性与提交快照。将每轮提交时间与该轮审批步骤关联，向有权限的日志详情返回时间线。
2. **员工信纸**：在底部左侧加入时间、目标输入区；草稿可保存，提交时显示字段错误；历史日志显示提交时的计划及最新星级。
3. **审批信纸**：完整展示员工计划和实际提交时间；在署名左侧加入三颗可选择的星；保存时与逐项批注一同提交，并在审批记录中显示各次选择、动作和精确到秒的时间。
4. **全员状态表**：增加所有角色可见的导航和日期表格；在用户管理中提供工号补录；确保未写日志的员工也出现，并限制表格接口只返回状态字段。领导查看详情复用现有授权校验，并阻止访问未提交的草稿内容。
5. **计划提醒**：沿用站内提醒机制，按计划完成时间和提前量向员工、对应领导分别发出提醒；复用定时检查和去重规则，保证改期重提可重新提醒而同一轮不重复。
6. **OSS 档案库**：增加版本快照与上传状态记录、私有 OSS 上传及重试；在领导侧边栏增加档案库和版本详情，读取时复用现有日志授权规则，验证图片和批注均属于所选历史版本；全员表的归档列仅在全部审批完成且当前轮最终审批版上传成功时变为“是”。
7. **校验与交付**：检查权限、空计划、三选一、退回重提、多级审批、旧日志、工号唯一性、全员列表、日期切换、北京时间和窄屏/打印；核对每轮提交与每级审批时间的秒级显示、顺序和历史留存，以及双向提醒的收件人、触发窗口和去重；检查 OSS 上传失败重试、历史版本不覆盖和无权限读取被拒绝；完成自动测试、构建和迁移校验，生成 Workbench 可上传的升级包及备份部署步骤。

## 九、验收标准

- 员工在今日信纸左下角填写计划完成时间与目标；缺任一项时可以保存草稿，但不能正式提交。
- 三颗星初始无色；有权限的审批人只能选择一个结果，红、绿、灰与文字含义一致；员工无法修改。
- 领导审批时看到完整信纸、计划、署名日期和逐项批注；员工可看到审批后的计划结果及每位审批人的记录。
- 旧日志无需补计划即可正常查看；退回重提不丢失历史计划快照和审批记录。
- 任一已登录角色都能查看选定日期的员工状态表；普通员工不能通过页面或接口读取其他人的日志内容。
- 只有拥有相应查看权限的领导账号能从已提交的行打开完整日志；无权限、无日志、草稿或退回修改中的行不能打开正文。
- 表格包含所有已启用员工，准确区分草稿、退回、已提交、审批中和已归档；无日志者显示两个“否”。
- 工号为独立字段；未补录时明确提示，重复工号不能保存。
- 新功能不改变现有工作项至少四条、每条至少 20 个非空白字符、图片及逐项批注规则。
- 员工提交后能看到自己的实际提交时间；每位部门主管或领导审批后，员工和有权限的审批人都能看到该审批人的姓名、动作及北京时间秒级时间。
- 多级审批分别留时，不以归档时间替代；退回与重新提交分轮留痕；草稿、待审批和缺失时间的旧记录不显示伪造时间。
- 员工选择未来的计划完成时间后，系统在到期前按设置的提前量给本人及对应领导各发一条站内提醒；无权限领导收不到该计划内容，重复调度不产生重复提醒。
- 计划改期并重新提交时按新时间重新提醒；草稿、退回待修改、已评定及过期计划不补发到期前提醒。
- 员工提交版与领导审批版都以完整、互不覆盖的历史版本进入私有 OSS；重提和多级审批保留各自版本，图片、计划、批注、星级与时间线可在对应版本中还原。
- 领导能在自己的系统侧边栏打开“云端档案库”，检索并查阅授权范围内的版本；普通员工和无权限领导不能通过界面或接口读取其他人的云端档案。
- OSS 暂时不可用时日志提交及审批记录仍保留，档案显示待上传或失败并可重试；未上传成功的版本不显示成已可查阅。
- 全员表“是否归档”在员工提交版上传、部分领导审批版上传、最终审批版待上传或上传失败时均为“否”；仅全部审批完成且本轮最终审批版上传成功后变为“是”。

## 十、设计口径

已确认：每份日志只填写一条工作计划，由审批人对这条计划三选一评星；部门主管就是现有“领导”角色，不另设角色；全员只能查看表格状态，日志正文仅有权限的领导可从表格进入。表格按“行只列员工、默认查询今天、工号独立于用户名”设计。工作计划提醒沿用现有系统设置的提前量（默认 30 分钟），与日志提交提醒共用该设置。云端档案库使用阿里云 OSS，领导须能从自身系统界面进入并查阅授权档案；全员表的“是否归档”只在全部审批完成且本轮最终审批版成功上传 OSS 后显示“是”。如你希望“完成工作日志”改为**仅领导审批通过才显示是**，也应在实施前调整状态口径。
